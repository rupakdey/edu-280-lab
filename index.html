Understand the HA design: active/standby, link health and traffic flow

What the two gateways actually provide

A single site supplies a common set of WAN, VLAN, forwarding and security settings to two separately activated virtual gateways. Normally ZTB-1 is Active and forwards branch traffic, while ZTB-2 is Standby and is ready to take over the forwarding role. This protects the branch against a gateway failure; it does not mean traffic is load-balanced across both gateways in this active/standby exercise.

Why GE4 and VRRP both appear

GE4 is the dedicated high-availability connection between the gateways. VRRP supports the active/standby gateway role on the LAN side, so clients can keep using the configured gateway address if the active unit fails. Each appliance still has its own network interfaces and activation state. HA depends on the required settings and links being healthy; provisioning both devices alone is not proof of successful failover.

How that fits with WAN and cloud security

The branch has two WAN interfaces (GE1 and GE2) for uplink resilience. Traffic that requires Zscaler cloud inspection traverses the appropriate service tunnels toward the Zero Trust Exchange; branch VLANs reach the ZTB gateway on GE6–GE8. A ZPA App Connector supports private-application connectivity, but it is separate from the VRRP HA mechanism. A second WAN path and a second gateway solve different failure scenarios.

i
What to verify in this lab

Confirm Active and Standby device states, the GE4/VRRP settings, LAN gateway availability, and the expected ZIA tunnel status. The source tasks validate configuration and health; a full cable-pull failover exercise is not assumed.

Two virtual gateways

ZTB-1 (primary) and ZTB-2 (secondary) provide HA. Each pod includes two WAN, three LAN, one management, and one HA interface.

Three internal zones

Subnet10: Windows server; Subnet20: IoT Ubuntu; Subnet30: OT1 and OT2 Linux hosts.

Cloud connectivity

Shared direct-internet links connect the branch to Zscaler services; an App Connector supports private-application access through ZPA.
