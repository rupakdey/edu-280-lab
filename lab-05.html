Technical context · Traffic steering

Policy-Based Routing: choosing the right path for each flow

Policy-Based Routing (PBR) lets a gateway choose a traffic path using policy criteria—not just a destination IP address. It is useful when a branch has multiple WAN links and must decide which connections should go directly to the internet, through ZIA, or toward private applications through ZPA.

Why use PBR instead of destination-only routing?

A conventional routing table typically selects a next hop from the destination address and longest matching prefix. That cannot readily express business requirements such as “send selected SaaS traffic from one network directly over the best WAN, but keep other internet traffic on the existing ZIA path.” PBR adds source network, destination/application object, protocol or port, and selected forwarding path as match conditions.

This matters for performance (low-latency paths for selected applications), resilience (more than one WAN interface), and security architecture (deliberately steering traffic through the intended Zscaler service or a direct path). A direct-internet route is a forwarding decision, not permission to bypass security controls unintentionally; organizations should review the inspection and access-policy implications of every exception.

How Zero Trust Branch evaluates a routing rule

ZTB first considers whether traffic matches the defined source, destination, and protocol or port. A matching policy then chooses a next-hop type such as LAN/WAN, ZIA, or ZPA. With two WAN interfaces, traffic distribution can select Best, Balanced, or None, according to the available settings. Best lets ZTB determine the preferred WAN dynamically; it is not a guarantee that GE1 always wins. Nonmatching flows continue through other applicable routing policies, including the default ZIA and ZPA paths.

What this lab proves

Before creating the rule, Lab 5 checks a host's normal Zscaler internet path. You then create an Adobe SaaS object and a rule for Subnet10 + Adobe + ICMP. Finally, you capture traffic on ge1 and ge2 to see which physical WAN carried the matching ping. A ping from Subnet30, which does not match the Subnet10 source condition, is compared against the existing ipsec0 cloud-forwarded path. The contrast verifies policy selection; it is more meaningful than simply observing a successful ping.

WAN selection and IPs vary

Do not copy example Adobe/CDN IP addresses or assume GE1 always wins. Resolve the address during the test and observe the actual best-score interface.

  1. On the site Interfaces → WAN view, identify the active gateway and its current best WAN score. The preferred interface can change.
  2. From the Windows Server (Subnet10), run ping adobe.com -t and record the IP address resolved by the ping.
  3. On the active gateway console, capture traffic on GE1 and GE2 using the actual Adobe IP from your session. Compare where ICMP packets appear.

    Commands: tcpdump -ni ge1 -c 5 host <Adobe-IP> and tcpdump -ni ge2 -c 5 host <Adobe-IP>.

  4. Stop the Windows ping. From OT1 (Subnet30), ping adobe.com; compare with a capture on the ZIA tunnel ipsec0.

    Command: tcpdump -ni ipsec0 -c 5 host <resolved-IP>.

  5. Optionally inspect iptables -t mangle -nvL PBR-RULES on the gateway to view matching packet counters.
