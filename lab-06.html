Technical context · Name resolution and policy

Why branch networks need DNS policies

Devices commonly connect to services by name, such as google.com, rather than by remembering IP addresses. A DNS query translates that name into an address. DNS policy gives a branch a controlled way to decide which DNS requests are answered, where they are forwarded, or which names are refused, based on the source network and requested domain.

What operational problem does DNS policy solve?

Different branch devices need different name-resolution behavior. Internal application names may require corporate resolvers, while ordinary public names can use designated external resolvers. Organizations may also want IoT/OT networks to avoid selected internet services or known risky domains, without deploying or configuring a DNS agent on every device. Centralized, source-aware DNS handling enables those controls and produces policy-level visibility into resolution requests.

ZTB distinguishes WAN DNS used for its own connectivity from private DNS used to resolve appropriate namespaces. Site DNS policies can match a source CIDR and a domain or domain-object group, then perform a specific action. This is a name-resolution control: it is related to, but not a replacement for, firewall rules that enforce actual network connectivity.

Understand the three important actions

ActionWhat it doesTypical reason
RedirectForwards a matching DNS query to a designated DNS gateway/resolverUse corporate DNS for private applications or a specified resolver for a network
OverrideReturns an administrator-configured IP address as the DNS answerProvide a controlled synthetic or test response for a domain
RejectRefuses the matching DNS request rather than providing the normal answerPrevent name resolution for an unwanted domain from selected devices

How Labs 6.1 and 6.2 demonstrate the difference

In Task 6.1, DNS queries for google.com originating from the OT network 10.1.30.0/24 receive the configured Override answer 8.8.8.8. That address is commonly used as a public DNS resolver; here it is deliberately used as an illustrative returned address. The task demonstrates response manipulation, not a correct production mapping for Google's website. The source PDF calls the exercise “Redirect Domain Traffic,” but the actual action configured is Override.

In Task 6.2, queries from the IoT network 10.1.20.0/24 for *.whatsapp.com are Rejected with DNS error code 5 (Refused). Because the match is source-scoped, the same domain need not receive the same treatment from every network. Baseline and post-policy lookups show whether the rule changed DNS behavior as intended.

What DNS blocking does not prove

A failed DNS lookup does not by itself establish that every path to a service is blocked. A device may retain a cached address or attempt access using an IP directly; alternate DNS behavior also depends on how the site intercepts and forwards queries. Use firewall, routing, and application controls as complementary enforcement layers. In this lab, the expected observation is the changed DNS response and resulting browser behavior, not proof of universal application isolation.

6.1

Override Google DNS responses for OT1

Create the Google domain object and a source-scoped DNS Override rule.

Documented navigation: Zero Trust Branch → Deployments → Sites → [Site Name] → DNS Policy → Configure. What Are Site DNS Policies? ↗ · Configuring Site DNS Policies ↗

Search menu → DNS Policies

If menu labels differ, use Search Menu. Source screenshots may show earlier navigation.

i
Source title versus configured action

The source labels this activity “Redirect Domain Traffic”, but its actual configured Action is Override. Follow the explicit configuration values.

  1. Open OT1 (Subnet30) and run nslookup google.com . Record the normal response before making changes.

  2. Documented navigation for objects: Zero Trust Branch → Resources → Objects. Adding Objects ↗. The source uses an older Objects & Groups path.

    Search menu → Objects
    Open Objects and create a Domains object for google.com.
    SettingRequired value
    Object NamePOD##-Google
    Domaingoogle.com
  3. Open the assigned site’s DNS Policy → Configure → Add Policy.
  4. Create the source-specific Override rule below.
    SettingRequired value
    Rule NamePOD##-Override-Google
    Sources10.1.30.0/24 (Subnet/Host)
    Destination DomainsPOD##-Google
    ActionOverride
    Override IP8.8.8.8
  5. Select Add and Commit, then repeat nslookup google.com on OT1.
✓
Expected result

OT1’s DNS lookup for google.com returns the configured override address 8.8.8.8. This is a DNS answer override, not a redirect to a DNS resolver.

6.2

Reject WhatsApp DNS requests from the IoT subnet

Block *.whatsapp.com lookups for the IoT host using DNS error code 5.

Documented navigation: Zero Trust Branch → Deployments → Sites → [Site Name] → DNS Policy → Configure. What Are Site DNS Policies? ↗ · Configuring Site DNS Policies ↗

Search menu → DNS Policies

If menu labels differ, use Search Menu. Source screenshots may show earlier navigation.

  1. Open the IoT Ubuntu VM (Subnet20), run nslookup web.whatsapp.com , and browse to web.whatsapp.com to establish normal resolution/access.

  2. Documented navigation for objects: Zero Trust Branch → Resources → Objects. Adding Objects ↗. The source uses an older Objects & Groups path.

    Search menu → Objects
    Create a Domains object named POD##-Whatsapp containing *.whatsapp.com.
    SettingRequired value
    Object NamePOD##-Whatsapp
    Domains*.whatsapp.com
  3. Open your site’s DNS Policy → Configure → Add Policy.
  4. Add a Reject policy with the following values.
    SettingRequired value
    Rule NamePOD##-Block-Whatsapp
    Sources10.1.20.0/24 (Subnet/Host)
    Destination DomainsPOD##-Whatsapp
    ActionReject
    Error Code5 — Query Refused
  5. Select Add and Commit. From IoT, retry ping web.whatsapp.com or nslookup web.whatsapp.com .
  6. Try web.whatsapp.com in the IoT browser and confirm that the site no longer loads.
✓
Expected result

DNS resolution for web.whatsapp.com is refused from Subnet20 and the web application is unavailable from that host.
