Technical context · Endpoint isolation

Macro versus microsegmentation — how ZTB stops lateral movement

A subnet boundary limits communication between network groups. ZTB's network-of-one model adds a boundary between individual endpoints, including OT devices in the same VLAN.

Why a traditional subnet boundary cannot isolate OT1 from OT2

Lab 2 filtered between Subnet10 and Subnet20. That is macrosegmentation: it treats the entire subnet as one policy group. But OT1 and OT2 both belong to 10.1.30.0/24. With conventional subnet masks, two peers in the same VLAN can exchange Ethernet frames locally without going through a routed firewall. A subnet-to-subnet rule elsewhere would not necessarily see that peer traffic.

What ZTB changes: one endpoint, one routed boundary

In the full Airgap / network-of-one protection model, ZTB uses intelligent DHCP assignment or supported static-device mechanisms to give an endpoint a /32 subnet mask. The endpoint regards other device addresses—even ones that share the familiar 10.1.30.x range—as destinations reached through its gateway. When ZTB is the gateway, peer-to-peer flows are therefore presented to the appliance for inspection and policy enforcement. That is how same-VLAN traffic becomes visible to ZTB rather than bypassing security by taking a direct Layer 2 path.

What the policy in this specific lab does

Lab 4 first proves OT1 can reach OT2. The source task then creates a site firewall Reject rule with both source and destination set to 10.1.30.0/24, using LAN Zone → LAN Zone. This is a rule for traffic within the entire OT subnet, not a host-specific rule listing OT1 and OT2 by their exact DHCP addresses. The /32 host model makes the flow inspectable; the broader source/destination match causes the policy to reject it. The next ping should fail and the custom rule’s hit counter should rise.

Important exception: not every asset uses /32 mode

Zscaler also documents Airgap-Lite, which keeps conventional subnet masks and can allow local peer communication, and Airgap+, which creates small micro-subnets where peers inside one micro-subnet may communicate directly. Those are different protection models. The Lab 4 observation of a /32 address is central to why this exercise can enforce intra-OT isolation.

4.1

Verify baseline OT endpoint reachability

Find OT2’s assigned /32 address and confirm OT1 can reach it before applying a new policy.

!
Do not hard-code the OT2 address

OT2 is DHCP-assigned. Use the real IP found in your POD, not an example shown in screenshots.

  1. In Zero Trust Branch Assets, locate the OT endpoint in 10.1.30.0/24. Note its actual DHCP address; it may be 10.1.30.20 or 10.1.30.21.
  2. If an endpoint is missing, check the gateway console with arp -a or run ifconfig on OT2. The source illustrates a /32 mask.
  3. Open the OT1 terminal and ping the actual OT2 IP you recorded.
✓
Expected result

OT1 can reach OT2 before the finer-grained intra-OT firewall rule is installed.

4.2

Reject traffic between OT endpoints

Create a site policy that isolates endpoints communicating within Subnet30.

Documented navigation: Firewall → Policies (Global / Template / Site Policies). Zscaler Help Portal ↗

Search menu → Firewall Policies

If menu labels differ, use Search Menu. Source screenshots may show earlier navigation.

  1. Open your assigned ZTB site and select Policies → Configure → Add Policy.
  2. Create the Reject rule using the exact subnet and zone values shown below.

4.3

Verify OT-to-OT isolation

Prove that the new firewall rule prevents lateral communication.

  1. Open OT1 in Skytap and ping the actual OT2 IP discovered in Task 4.1.
  2. Return to the policy listing and verify that the custom rule’s hit count increases.
✓
Expected result

The OT1-to-OT2 ping fails and the intra-OT policy hit count increases.
