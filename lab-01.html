Zero Trust Branch Device Interface Configuration

Create a Zero Trust Branch virtual HA site, onboard the primary and secondary gateways, then verify site services and provision a ZPA App Connector. Complete LAN/VLAN configuration and enable the secondary GE2 WAN interfaces to prepare for later segmentation and routing labs.

9 tasks Source Lab 1: about 45 minutes Complete Lab 1 Assigned POD + Skytap
Lab objectives

What you will accomplish

  • Create a site from vm-ha-edu280.
  • Activate ZTB-1 as Active and ZTB-2 as Standby.
  • Verify Debug/DNS/NAT/VRRP/DHCP/IPSec and connect the pre-provisioned ZPA App Connector.
  • Configure LAN interfaces GE6–GE8 and secondary WAN GE2 on both gateways.
Technical context

How a Zero Trust Branch HA site fits together

An HA site comprises two separately activated gateways sharing site policy, but with distinct forwarding roles. The GE4 HA link and VRRP help retain the LAN gateway service during a unit failure; GE1/GE2 provide separate WAN path resilience. ZIA service tunnels and ZPA App Connector connectivity solve different connectivity needs. Verify Active/Standby health and committed settings—not merely that two devices appear in the portal.

01 · Site

Common configuration

Begin with a site cloned from the vm-ha-edu280 template. The site is the management unit for its HA pair.

02 · Gateways

Active / Standby

Activate each virtual gateway separately. An HA interface (ge4) and VRRP settings support the pair.

03 · Services

Traffic and private access

ZIA IPSec provides the service-forwarding path; the ZPA App Connector adds private-application connectivity.

Read the roles separately

Active/standby means one device normally forwards while the partner waits to take over. It is different from active/active load sharing. The site’s policy and interface settings provide a shared configuration, but activation and operational state are per device.

GE4, VRRP and uplink redundancy

GE4 connects the two appliances for HA coordination. VRRP supports continuity of the LAN-side gateway role when a failover occurs. Two WAN links (GE1 and GE2) improve internet-uplink resilience; they are not substitutes for a standby gateway. Cloud forwarding to ZIA and private connectivity through ZPA are downstream services, not mechanisms that elect the active HA unit.

What the lab proves: both devices enrolled, expected Active/Standby role, VRRP/HA settings in place and tunnel health. The steps do not claim to demonstrate a physical link-disconnect failover test.

1.2

Activate the Active Device

Onboard ZTB-1 as the primary gateway and confirm that it reaches Active status.

Documented path: Open the site from Zero Trust Branch → Deployments → Sites, then use that site’s activation controls.

Search menu → Sites

Official documentation: HA-cluster deployment ↗ · Managing Sites ↗
The HA guide may show the older Infrastructure → Connectors → Edge → Sites route.

  1. Open your new site in Sites and use its activation-code control for the primary gateway. Keep the code temporarily in a private local note.
  2. Open ZTB-1 in Skytap. Sign in at the console using admin and the lab-provided initial password a!rg@p. When prompted, change that initial password and keep the new value private.
  3. At the gateway menu, select 2 — Configure Gateway, then 1 — Configure Network.
  4. Configure the primary WAN as DHCP, then apply the change when prompted.
    Setting Required value / action
    WAN interfacege1
    WAN VLAN ID1
    Use DHCP for WANy
    Use DHCP for WAN nameserversy
    Apply configurationy
  5. Check that the configuration reports OK, return to the main menu (option 4 in the configuration submenu), then choose 1 — Activate Gateway and 1 — Activate Airgap Gateway. Enter the copied activation code.
  6. Return to the Experience Center site inventory and wait for the primary gateway to move from Post-update to Active. The source notes this can take about 15 minutes.
✓
Expected result

The ZTB-1 gateway is associated with the site and eventually shows Active after the post-update stage. If it has not changed after the documented wait, check its console and request instructor assistance.

1.3

Activate the Standby Device

Onboard the second gateway with the same WAN configuration to establish the HA pair.

Documented path: Open the site from Zero Trust Branch → Deployments → Sites, then use that site’s activation controls.

Search menu → Sites

Official documentation: HA-cluster deployment ↗ · Managing Sites ↗
The HA guide may show the older Infrastructure → Connectors → Edge → Sites route.

  1. In the same site, obtain the activation code for the standby gateway. Do not reuse a stale or previously consumed code.
  2. Open ZTB-2 in Skytap. Sign in as admin with the lab-provided initial password a!rg@p, and change it when required.
  3. Choose 2 — Configure Gateway → 1 — Configure Network. Set ge1, VLAN 1, DHCP for the WAN address (y), and DHCP for WAN name servers (y). Apply the changes (y).
  4. Verify the configuration, return to the main menu (configuration option 4), then choose 1 — Activate Gateway → 1 — Activate Airgap Gateway. Enter the standby code from this site.
  5. In Sites, wait for Post-update to progress to Standby; allow approximately 15 minutes according to the source.
✓
Expected result

Both gateways are enrolled in the site; the primary reads Active and the secondary reads Standby.

1.4

Validate and Configure Site-Level Settings

Validate branch services and connect the pre-provisioned ZPA App Connector.

Documented path: Zero Trust Branch → Deployments → Sites → select your site; locate its Settings, DNS, Network and integration tabs in the live UI.

Search menu → Sites

Official documentation: Managing Sites ↗ · HA-cluster deployment ↗
For the ZPA provisioning key: Infrastructure → Private Access → Component → App Connector Keys (App Connector provisioning keys ↗).

  1. Open the configured site POD##-Student-Lab and locate Settings → Debug Options in the assigned lab UI (the PDF is the source for this site-level sub-tab). Enable Debug Logs and verify WAN SSH is disabled for both gateways.
    Search menu → Zero Trust Branch
  2. In DNS, verify the WAN resolvers and set the private resolvers below; save the settings.
    Setting Required value / action
    WAN DNS server 11.1.1.1
    WAN DNS server 28.8.8.8
    Private DNS server 110.73.50.20
    Private DNS server 210.73.50.21
  3. Open NAT, switch NAT to Enable, and accept the confirmation.
  4. Open VRRP. The course screenshot shows VRRP Group ID 155 and interface ge4 [ha] selected for both gateways; confirm these values in your assigned POD before saving.
  5. Under DHCP Service, verify that DHCP Server is selected.
  6. In the site’s ZIA → IPSec Tunnels view, confirm tunnel status is Established or Up.
  7. Find App Connector Keys in Experience Center. Filter for your POD ID (for example pod01) and copy the existing provisioning key assigned to your POD. Treat the key as a secret; do not paste it into notes or screenshots for publication.
    Search menu → App Connector Keys
  8. Return to Zero Trust Branch → Deployments → Sites (or search Sites), select the site, and find its Settings → ZPA → Add control in the lab environment. This internal tab sequence comes from the lab PDF; verify it in the live UI.
  9. Name the connector pod##StudentAppC (replace ## with your POD number), paste the provisioning key, then Save.
  10. Wait a few minutes for the connector to show Connected under the ZPA tab.
  11. Open VLANs and inspect the preconfigured interfaces. This pilot stops here: the configuration of additional LAN and WAN interfaces begins in source Task 1.5.
✓
Expected result

Site Debug Logs are enabled while WAN SSH remains disabled; DNS, NAT, VRRP, DHCP and IPSec have been reviewed; the App Connector shows Connected; preconfigured VLANs are visible.
