Configure Ransomware Kill Switch Policy

Stage Green/Orange SSH rules, test incident-response containment, then restore normal mode.

3 tasksOptional lab~25 minutesAssigned POD + Skytap
Lab objectives

What you will accomplish

  • Create and validate a Green-mode SSH Accept policy.
  • Clone an Orange-mode Reject policy and set its order.
  • Activate Orange, demonstrate SSH blocking, check hits, and return to Green.
Technical context · Incident containment

What is a ransomware Kill Switch and why use one?

A ransomware outbreak can spread when compromised systems can reach additional devices over remote administration or file-sharing protocols. Waiting to edit dozens of firewall rules individually can delay containment. Zero Trust Branch's Ransomware Kill Switch provides a rapid, site-scoped mechanism for changing which preconfigured security policies are enforced at a selected threat level.

Why severity modes are useful

A normal operating posture may permit administrative connections needed for maintenance. During an incident, security teams may want to reduce lateral movement quickly while preserving approved essential services. ZTB uses severity Green → Yellow → Orange → Red, from lowest to critical risk. Rules can be associated with a severity level in advance, allowing a deliberate response when an incident threshold is reached. Switching modes is an operational security action, not simply a cosmetic status change.

How does enforcement work?

Each firewall policy has its matching criteria: zones, source and destination objects, and protocol/port. A policy can additionally be associated with a Kill Switch color. The site’s selected Kill Switch level changes which corresponding rules are effective. Rule ordering still matters within the applicable policy evaluation; a test must examine both current mode and policy match/order rather than assume every rule is universally active.

For this lab, an Accept SSH policy is associated with Green and a cloned Reject SSH policy with Orange. Both match LAN_ZONE to LAN_ZONE, Network → Private Subnets for source/destination, and TCP port 22. These object selections are broader than “only Windows Server to OT1”; they can match other qualifying private-subnet SSH flows. In production, tighten source and destination scopes to the workloads and business needs.

What the learner should prove

First, an SSH connection from the Windows Server in Subnet10 to 10.1.30.10 in Subnet30 succeeds while Green mode is active. Next, after installing the Orange Reject rule and changing the site to Orange, the same SSH attempt should fail and the matching block-policy hit count should increase. The source guide illustrates “connection refused”; the exact client-side symptom can vary by action and network conditions.

Containment is not remediation. A Kill Switch cannot remove malware or replace investigation, endpoint isolation, restoration, and incident-response procedures. In the training environment, return the site to Green after validation so later activities are not unexpectedly disrupted.

9.1

Create and validate Green-mode SSH access

Install a preconfigured Allow rule and establish the baseline SSH session.

Documented navigation: Firewall → Policies → Site Policies → Configure. Configuring Firewall Policies ↗

Search menu → Firewall Policies

The source PDF shows a site-specific Policies tab under an older Sites path. The official Configuring Firewall Policies article documents the Site Policies scope; use the equivalent view in your tenant.

  1. Open the Site Policies view under Firewall → Policies and select the policy scope for POD##-Student-Lab . Choose Configure → Add Policy. If the live tenant exposes policies within the site detail page, use that verified equivalent.
  2. Enter the following policy configuration, replacing ## with your POD number:
    SettingValue
    ActionAccept
    NamePOD##-Allow-ssh
    Source ZoneLAN_ZONE | LAN Zone
    Destination ZoneLAN_ZONE | LAN Zone
    SourceNetwork → Private Subnets
    DestinationNetwork → Private Subnets
    PortsCustom Port → tcp:22 (SSH)
    Ransomware Kill SwitchGreen
  3. Click Add, then Commit to activate the new policy.
  4. On the Windows Server (Subnet10) Skytap VM, open Command Prompt and run ssh zscaler@10.1.30.10 . Enter the training-host password Zscaler123! when prompted; if it asks to trust the SSH host key, verify you are connecting to the lab host and enter yes. Exit the SSH session after successful login.
  5. Return to the policy list and verify the allow rule’s hit count is greater than zero after the test.
✓
Expected Result

SSH from the Windows Server to 10.1.30.10 succeeds while the site is in Green mode, and the Green policy hit count increases.

9.2

Clone and stage the Orange SSH block rule

Create the conditional Reject rule and place it in the prescribed order.

Documented navigation: Firewall → Policies → Site Policies → Configure. Configuring Firewall Policies ↗

Search menu → Firewall Policies

The source PDF shows a site-specific Policies tab under an older Sites path. The official Configuring Firewall Policies article documents the Site Policies scope; use the equivalent view in your tenant.

  1. In the site policy list, open the gear/action menu on POD##-Allow-ssh and choose Clone.
  2. Edit the cloned policy with the following values; keep the inherited source/destination criteria and port intact:
    SettingValue
    ActionReject
    NamePOD##-Block-ssh
    Source ZoneLAN_ZONE | LAN Zone
    Destination ZoneLAN_ZONE | LAN Zone
    SourceNetwork → Private Subnets
    DestinationNetwork → Private Subnets
    PortsCustom Port → tcp:22 (SSH)
    Ransomware Kill SwitchOrange
  3. Click Clone to create the new rule, then Commit the changes.
  4. Click Reorder, move POD##-Block-ssh to position 2 as shown in the source guide, then click Save Policy Order. Confirm the current effective ordering before continuing.
  5. Confirm both the Green Accept rule and Orange Reject rule are present with the intended match criteria and color assignments. Do not change the Kill Switch mode until ready to test.
✓
Expected Result

Both SSH rules are committed. The Orange Reject rule is ordered second and retains the intended zones, objects, protocol, and Orange association.

9.3

Activate Orange, verify SSH blocking, restore Green

Prove containment behavior without leaving the lab in an escalated state.

Documented navigation: Policies → Access Control → Segmentation → Kill Switch. Configuring the Ransomware Kill Switch for a Site ↗

Search menu → Kill Switch

This breadcrumb is taken from current Zscaler Help. Confirm the selected POD/site before changing its threat level.

!
Potential service disruption

Changing the Kill Switch level affects the selected site and can block legitimate traffic. Perform this exercise only in your assigned training POD and return to Green afterwards.

  1. Open Policies → Access Control → Segmentation → Kill Switch, select your assigned POD/site, turn the dial to Orange, enter orange in the confirmation prompt, and click Confirm.
  2. Confirm the site’s overview or banner shows the Kill Switch is ON / Orange for the assigned POD.
  3. From the same Windows Server, repeat ssh zscaler@10.1.30.10 . The connection should fail under the Orange Reject rule. Record the observed error rather than assuming every client shows identical wording.
  4. Return to the policy list and verify that the Reject/Block SSH rule has a nonzero hit count following the test.
  5. Restore Green mode: return to the Kill Switch page for the correct site, select Green and confirm. Recheck the site indicator. The source guide recommends this restoration after testing.
✓
Expected Result

Orange mode becomes active; SSH is blocked and the Reject rule records matching hits. The site is returned to Green after testing.
